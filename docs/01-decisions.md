# 1차 MVP 결정 기록

> 문서 상태: 1차 MVP 구현 전의 초기 설계 기준선이다. 최종 불변 문서가 아니며, 구현과 테스트에서 새로운 사실이 확인되면 갱신한다.

## 결정 상태 표기

| 표기 | 의미 |
|---|---|
| **확정** | 현재 승인된 범위 또는 업무 규칙이다. 변경하려면 근거와 영향 범위를 다시 검토한다. |
| **초기안** | 구현을 시작하기 위한 임시 기준이다. 구현 과정에서 더 적절한 안으로 바꿀 수 있다. |
| **추천안** | 현재 정보에서 우선 검토할 선택지다. 채택이 확정된 것은 아니다. |
| **열린 결정** | 구현 전에 또는 구현 중에 선택해야 하며 아직 결론 내리지 않은 항목이다. |

문서에서 별도 표기가 없는 범위와 업무 규칙은 **확정**으로 본다. 타입, 길이, URI, 패키지와 구현 기술처럼 명시적으로 확정되지 않은 세부사항은 이 문서만으로 확정하지 않는다.

## 프로젝트 목표와 진행 단계

### 프로젝트 목표 — 확정

풋살 매치 모집·참가에서 시작해 향후 코트 예약, 결제, 취소와 환불까지의 상태와 업무 규칙을 모델링한다. 동시 요청과 외부 시스템 실패 상황에서도 데이터 정합성을 유지하는 풋살 예약·매칭 플랫폼을 지향한다.

### 전체 진행 단계 — 확정

1. 1차 MVP 기능 구현
2. 2차 MVP 기능 구현
3. 인프라·배포·운영 환경 구성
4. 성능 측정과 병목 개선
5. 포트폴리오 문서화

현재 설계 대상은 1차 MVP뿐이다. 이후 단계는 방향만 기록하고 상세 API, 테이블 또는 구현 기술을 미리 설계하지 않는다.

## 1차 MVP 범위 — 확정

| 영역 | 포함 기능 |
|---|---|
| 회원·인증 | 회원가입, 로그인, 로그아웃, 현재 로그인 회원 조회, 최소 프로필 조회·수정 |
| 구장·코트 | 미리 준비한 구장 목록·상세 조회, 구장에 속한 코트 조회 |
| 매치 | 목록·상세·기본 검색과 필터, 개설·수정, 모집 마감·재개, 취소, 내가 주최한 매치 조회 |
| 참가 | 참가·취소·조건부 재참가, 내가 참가한 매치 조회, 주최자의 참가자 목록 조회, 중복 참가·정원 초과 방지 |

핵심 가치는 `매치 탐색 → 상세 조회 → 참가 → 정원 확보 → 내 참가 매치 확인 → 참가 취소 → 정원 복구` 흐름과 그 과정의 정합성이다. 주최자는 `로그인 → 구장·코트 조회 → 매치 개설 → 참가자 확인 → 수정 또는 모집 마감 → 필요 시 매치 취소` 흐름을 수행한다.

## 2차 MVP 이후 범위와 1차 MVP 제외 사항 — 확정

다음 항목은 삭제된 요구가 아니라 2차 MVP 이후의 후보이다. 1차 MVP API와 데이터 모델에는 포함하지 않는다.

- 팀 생성·팀원 관리와 팀 가입 승인
- 대기자와 자동 승급, 참가 승인제, 자동 매칭 알고리즘
- 알림, 후기·평가, 노쇼, 신고·제재
- 운영자 관리 기능
- 실제 코트 시간대 예약
- 결제, 환불, PG 웹훅
- 운영 인프라·배포 구성과 성능 최적화 상세

## 승인된 결정

### 사용자와 권한 — 확정

- 핵심 사용자는 개인 참가자다. 일반 회원도 매치를 개설할 수 있다.
- Host와 Participant는 전역 역할이 아니라 회원과 특정 매치 사이의 서로 독립된 관계다.
- 전역 Role 후보는 `USER`, `ADMIN`이다. 1차 MVP에는 운영자 관리 기능을 넣지 않는다.
- 매치 목록·상세와 구장·코트 조회는 비회원에게 공개한다.
- 매치 개설·수정·취소, 모집 마감·재개, 참가·참가 취소는 로그인이 필요하다.
- 매치 수정·모집 마감·모집 재개·매치 취소·참가자 목록 조회는 해당 매치 주최자만 할 수 있다.

### 구장과 코트

- **확정:** 1차 MVP는 운영자가 미리 준비한 구장과 코트 데이터를 사용하며 일반 사용자의 구장 등록은 제외한다.
- **초기안:** 초기 데이터 지역은 경기도 일부를 후보로 삼는다. 지역 모델 자체를 경기도로 하드코딩하지 않는다.
- **확정:** Match는 Court만 참조하고 Venue를 중복 참조하지 않는다.
- **확정:** Court 정보는 실제 대관 가능 여부를 보장하지 않는다. 실제 코트 시간대 예약은 1차 MVP 범위가 아니다.

### 매치와 모집

- **확정:** 1차 MVP의 업무 상태명은 Match `SCHEDULED`·`CANCELLED`, 모집 `OPEN`·`CLOSED`다. 저장 타입과 Java enum 구현 방식은 초기안으로 남긴다.
- **확정:** 취소된 매치 또는 `현재 시각 >= startAt`인 매치에는 참가할 수 없다.
- **확정:** `현재 시각 >= startAt`이면 참가 취소도 허용하지 않는다.
- **확정:** 취소된 매치는 재활성화하지 않는다.
- **확정:** 주최자는 시작 전 모집을 마감하거나 재개할 수 있다. 모집 재개는 남은 자리가 있을 때만 가능하다.
- **확정:** 정원을 늘려도 `CLOSED`를 자동으로 `OPEN`으로 바꾸지 않는다.
- **확정:** `endAt`은 `startAt`보다 뒤여야 한다.
- **확정:** 기본 탐색 목록은 `SCHEDULED`, `OPEN`, 시작 전, 남은 자리 있음 조건을 모두 만족하는 매치다. 모집 마감 또는 정원 마감 매치는 필터로 조회할 수 있고, 취소되거나 이미 시작한 매치는 일반 탐색 목록에서 제외한다.

정원 도달이나 매치 취소 시 모집 상태 컬럼까지 자동으로 `CLOSED`로 바꿀지는 승인된 규칙만으로 정해지지 않았다. 참가 가능 여부는 Match 상태, 모집 상태, 시간과 남은 자리 조건을 모두 검사해 판단한다.

### 주최자 참가 — 확정

- 주최자는 매치에 직접 참가할지 선택할 수 있다.
- 참가하는 주최자도 일반 참가자와 동일하게 정원에 포함한다.
- 주최자 참가를 Match의 boolean 값 하나로 표현하지 않고 MatchParticipation 관계로 표현한다.
- 주최자가 자신의 참가를 취소해도 주최자 관계는 유지한다.

### 매치 수정

- **확정:** 해당 주최자만 수정할 수 있고, 취소되었거나 이미 시작한 매치는 수정할 수 없다.
- **확정:** 정원 감소 결과가 `CONFIRMED` 참가자 수보다 작아질 수 없다.
- **확정:** 정원 증가로 `CLOSED` 상태를 자동 해제하지 않는다.
- **초기안:** 제목과 안내 사항은 시작 전까지 수정할 수 있다.
- **초기안:** 권장 실력, 코트와 시간은 주최자를 제외한 활성 일반 참가자가 없을 때만 수정할 수 있다.

초기 수정 정책은 구현 과정에서 실제 사용 흐름과 정합성 위험을 확인한 뒤 재검토할 수 있다.

### 참가 상태와 전이

상태명과 아래 업무 전이는 **확정**이다. 저장 타입과 Java enum 구현 방식은 초기안으로 남긴다.

| 현재 상태 | 사건 | 다음 상태 | 허용 조건 |
|---|---|---|---|
| 참가 관계 없음 | 최초 참가 | `CONFIRMED` | 매치가 참가 가능하고 남은 자리가 있음 |
| `CONFIRMED` | 회원의 참가 취소 | `CANCELLED_BY_MEMBER` | `현재 시각 < startAt` |
| `CANCELLED_BY_MEMBER` | 재참가 | `CONFIRMED` | 매치가 참가 가능하고 남은 자리가 있음 |
| `CONFIRMED` | 매치 취소 | `CANCELLED_BY_MATCH` | 주최자가 매치를 취소함 |
| `CANCELLED_BY_MATCH` | 재참가 | 전이 없음 | 항상 불가 |

- **확정:** 한 회원은 한 매치에 하나의 참가 관계만 가진다.
- **추천안:** DB에서 `UNIQUE(match_id, member_id)`로 관계 중복을 방지한다.
- **확정:** 중복 참가 요청으로 활성 관계가 중복 생성되어서는 안 된다.
- **확정:** 중복 취소로 논리적 남은 자리가 두 번 복구되어서는 안 된다.
- **확정:** 매치 취소 시 모든 활성 참가를 `CANCELLED_BY_MATCH`로 변경한다.
- **확정:** 매치 취소와 활성 참가 변경은 하나의 유스케이스 트랜잭션에서 함께 성공하거나 함께 롤백한다.

### 정원 불변식 — 확정

- 활성 참가자는 `status = CONFIRMED`인 참가 관계만을 뜻한다.
- 활성 참가자 수는 `maxParticipants`를 초과할 수 없다.
- 논리적 남은 자리 `maxParticipants - 활성 참가자 수`는 0보다 작을 수 없다.
- 실패한 참가 요청은 참가 상태와 정원에 영향을 주지 않는다.
- 주최자 관계와 참가 관계는 독립적이다. 주최자도 `CONFIRMED` 참가 관계가 있을 때만 정원에 포함한다.

현재 참가 인원 또는 남은 자리를 저장할지, 조회 시 집계할지는 열린 결정이다. 위 불변식은 어떤 저장 방식을 선택해도 지켜야 한다.

### 권장 실력

- **확정:** 권장 실력은 안내 정보이며 참가 제한 조건이 아니다. 성별, 연령 또는 실력을 자동 비교해 참가를 제한하지 않는다.
- **초기안:** 코드 후보는 `ANY`, `INTRODUCTORY`, `BEGINNER`, `INTERMEDIATE_OR_ABOVE`다.

## 의도적으로 미리 결정하지 않는 구현 기술

다음 수단은 문제와 재현 조건을 확인하기 전에는 채택하지 않는다.

- 비관적 락, 낙관적 락, 조건부 원자적 UPDATE
- 멱등성 키
- Redis, 캐시, 메시지 큐, 비동기 이벤트, Outbox
- 분산 락, 마이크로서비스, CQRS

마지막 자리 동시 참가를 포함한 정합성 문제는 `위험 확인 → 불변식과 재현 조건 정의 → 후보 비교 → 선택과 트레이드오프 기록 → 구현과 테스트 → 결과에 따른 설계 수정` 순서로 해결한다.

## 열린 결정

`현재 추천안`은 구현 계약이 아니다. 추천이 없는 항목은 근거를 모을 때까지 결론을 유보한다.

| 항목 | 현재 상황 | 선택지 | 현재 추천안 | 결정 시점 | 변경 영향 |
|---|---|---|---|---|---|
| 참가 인원 계산·저장 | 활성 참가자는 `CONFIRMED`로 정의됐지만 계산 방식은 미정 | matches에 현재 인원 저장 / 참가 행을 매번 집계 / 혼합 | 없음 | PAR-001 저장·조회 설계 전 | Match 필드, 쿼리, 갱신 책임, 동시성 테스트 |
| 마지막 자리 동시 참가 | 정원 초과 금지만 확정 | 비관적 락 / 낙관적 락 / 조건부 UPDATE / 다른 정합성 수단 | 없음 | 동시 참가 재현 테스트 후 | 트랜잭션, Repository 쿼리, 오류 처리 |
| 참가 취소 중복 요청 응답 | 자리가 두 번 복구되면 안 된다는 결과만 확정 | 성공으로 멱등 처리 / 상태 충돌 반환 | 없음 | PAR-002 API 계약 확정 전 | HTTP 상태, 오류 코드, 재시도 방식 |
| Repository 인터페이스 위치 | 모듈 경계만 설계함 | domain / application / infrastructure 경계 | 없음 | 첫 수직 기능 구현 시 | 의존 방향, 테스트 대역, 패키지 |
| 세부 내부 패키지명 | 문서에는 추천 구조만 존재 | 계층형 / 기능 중심 변형 | 없음 | 각 수직 기능 구현 시 | import와 가시성, 모듈 책임 |
| 회원 상태 enum | 탈퇴·정지 정책이 1차 MVP에 없음 | 상태 컬럼 미도입 / 최소 enum 도입 | 없음 | 회원 생명주기 요구가 생길 때 | 로그인 허용, 데이터 보존, API 응답 |
| 닉네임 중복 허용 | 프로필에 닉네임이 필요하나 유일성은 미승인 | 중복 허용 / 전역 유일 | 없음 | 회원가입·프로필 검증 구현 전 | DB 제약, 오류 코드, UX |
| 문자열 길이 최종값 | API 문서에 임시 상한이 필요함 | 초기 후보값 유지 / 사용 사례에 따라 조정 | 없음 | DTO·DB 컬럼 구현 전 | 검증, 컬럼 타입, 호환성 |
| 최대 정원 상한 | 최소 1 후보 외 상한 근거가 없음 | 상한 없음 / 업무 상한 설정 | 없음 | MAT-003 검증 구현 전 | 검증, 오류 응답, 부하 범위 |
| 시간 저장·타임존 | 시간 비교 규칙만 확정 | UTC 기반 / 지역 오프셋 보존 / 다른 정책 | 없음 | Match 시간 영속화 전 | DB 타입, JSON 형식, 비교와 테스트 |
| 성공 응답 공통 래퍼 | 성공 계약 형식이 미정 | 리소스 직접 반환 / 공통 data 래퍼 | 래퍼 없이 직접 반환 | API 초기 계약 검토 시 | 모든 성공 응답과 클라이언트 파싱 |
| 페이지 시작 번호 | 목록 페이징 기준이 미정 | 0부터 / 1부터 | 0부터 시작 | 목록 API 구현 전 | Query parameter, 응답 메타데이터 |
| 최종 정렬 규칙 | 기본 탐색 조건만 확정 | 시작 시간·생성 시간 등 | `startAt ASC, id ASC` 초기안 | MAT-001 조회 쿼리 구현 전 | 결과 안정성, 복합 인덱스 |

## 재검토 조건

다음 중 하나가 발생하면 관련 초기안·추천안과 열린 결정을 다시 검토한다.

- 동시 참가 테스트에서 정원 불변식 위반 또는 과도한 충돌이 재현됨
- 참가 취소·재참가 또는 매치 취소 트랜잭션에서 부분 성공 가능성이 발견됨
- 실제 조회 요구가 현재 상태·필터·정렬 후보로 표현되지 않음
- 세션 인증과 CSRF 흐름이 사용하는 클라이언트 형태와 맞지 않음
- DB 제약 또는 JPA 매핑만으로 승인된 상태 전이를 안전하게 표현하기 어려움
- 2차 MVP의 예약·결제·환불 요구가 현재 도메인 경계에 영향을 줌
- 구현·테스트 결과와 문서가 다름

재검토 시 해결책부터 고정하지 않는다. 문제와 불변식을 먼저 기록하고, 후보와 트레이드오프를 비교한 뒤 선택·테스트 결과와 함께 이 문서를 갱신한다.
