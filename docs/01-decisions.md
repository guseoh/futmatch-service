# 1차 MVP 결정 기록

> 문서 상태: 구현을 시작하기 위한 초기 설계 기준선이다. 구현과 테스트에서 새로운 사실이 확인되면 갱신한다.

## 결정 상태

| 표기 | 의미 |
|---|---|
| **확정** | 현재 승인된 범위 또는 업무 규칙 |
| **초기안** | 구현을 시작하기 위한 임시 기준 |
| **추천안** | 현재 정보에서 우선 검토할 선택지 |
| **열린 결정** | 구현 전 또는 구현 중 결론이 필요한 항목 |

타입, 길이, URI, 내부 패키지와 구현 기술은 명시적으로 확정하지 않은 한 초기안으로 본다.

## 프로젝트 목표와 진행 단계

### 프로젝트 목표 — 확정

풋살 매치 모집·참가에서 시작해 향후 코트 예약, 결제, 취소와 환불까지의 상태와 업무 규칙을 모델링한다. 동시 요청과 외부 시스템 실패 상황에서도 데이터 정합성을 유지하는 풋살 예약·매칭 플랫폼을 지향한다.

### 전체 진행 단계 — 확정

1. 1차 MVP 기능 구현
2. 2차 MVP 기능 구현
3. 인프라·배포·운영 환경 구성
4. 성능 측정과 병목 개선
5. 포트폴리오 문서화

현재 설계 대상은 1차 MVP뿐이다. 이후 단계는 방향만 기록하고 상세 API, 테이블과 구현 기술을 미리 확정하지 않는다.

## 1차 MVP 범위 — 확정

| 영역 | 포함 기능 |
|---|---|
| 회원·인증 | 회원가입, 로그인, 로그아웃, 현재 로그인 회원 조회, 최소 프로필 수정 |
| 구장·코트 | 미리 준비한 구장 목록·상세 조회, 구장에 속한 코트 조회 |
| 매치 | 목록·상세·기본 필터, 개설·수정, 모집 마감·재개, 취소, 내가 주최한 매치 조회 |
| 참가 | 참가·취소·조건부 재참가, 내가 참가한 매치 조회, 주최자의 참가자 목록 조회, 중복 참가·정원 초과 방지 |

핵심 흐름은 다음과 같다.

```text
매치 탐색
→ 상세 조회
→ 참가
→ 정원 확보
→ 내 참가 매치 확인
→ 참가 취소
→ 정원 복구
```

## 2차 MVP 이후 범위 — 확정

다음 항목은 삭제된 요구가 아니라 2차 MVP 이후 후보이며, 1차 MVP API와 데이터 모델에는 포함하지 않는다.

- 팀 생성·팀원 관리와 가입 승인
- 대기자와 자동 승급, 참가 승인제, 자동 매칭
- 알림, 후기·평가, 노쇼, 신고·제재
- 운영자 관리 기능
- 실제 코트 시간대 예약
- 결제, 환불, PG 웹훅
- 운영 인프라·배포 구성과 성능 최적화 상세

## 승인된 결정

### 사용자와 권한 — 확정

- 핵심 사용자는 개인 참가자다.
- 일반 회원도 매치를 개설할 수 있다.
- Host와 Participant는 전역 Role이 아니라 특정 매치와의 관계다.
- 전역 Role 후보는 `USER`, `ADMIN`이다.
- 매치 목록·상세와 구장·코트 조회는 공개한다.
- 매치 개설·수정·취소, 모집 마감·재개, 참가·참가 취소는 로그인이 필요하다.
- 매치 수정·모집 마감·재개·취소와 참가자 목록 조회는 해당 주최자만 가능하다.

### 구장과 코트

- 운영자가 준비한 구장과 코트 데이터를 사용한다.
- 초기 데이터는 경기도 일부 지역을 후보로 하되, 지역 모델을 경기도에 하드코딩하지 않는다.
- Match는 Court만 참조하고 Venue를 중복 참조하지 않는다.
- Court 정보는 실제 대관 가능 여부를 보장하지 않는다.

### 매치와 모집

- Match 상태는 `SCHEDULED`, `CANCELLED`다.
- 모집 상태는 `OPEN`, `CLOSED`다.
- 취소된 매치 또는 `현재 시각 >= startAt`인 매치에는 참가할 수 없다.
- `현재 시각 >= startAt`이면 참가 취소도 할 수 없다.
- **현재 시각이 시작 시각 이상이면 주최자도 매치를 취소할 수 없다.**
- 취소된 매치는 재활성화하지 않는다.
- 주최자는 시작 전에 모집을 마감하거나 재개할 수 있다.
- 모집 재개는 남은 자리가 있을 때만 가능하다.
- 정원을 늘려도 `CLOSED`가 자동으로 `OPEN`이 되지 않는다.
- `endAt`은 `startAt`보다 뒤여야 한다.
- 기본 탐색 목록은 `SCHEDULED`, `OPEN`, 시작 전, 남은 자리 있음 조건을 모두 만족한다.
- 모집 마감 또는 정원 마감 매치는 명시적 필터로 조회할 수 있다.
- 취소되거나 시작한 매치는 일반 탐색 목록에서 제외한다.

정원 도달이나 매치 취소 시 모집 상태 컬럼까지 자동으로 `CLOSED`로 바꿀지는 열린 결정이다. 참가 가능 여부는 Match 상태, 모집 상태, 시간과 남은 자리를 함께 검사한다.

### 주최자 참가

- 주최자는 매치에 직접 참가할지 선택할 수 있다.
- 참가하는 주최자는 일반 참가자와 동일하게 정원에 포함된다.
- 주최자 참가 여부를 Match boolean 컬럼으로 표현하지 않는다.
- 참가하는 주최자는 MatchParticipation으로 표현한다.
- 주최자가 자신의 참가를 취소해도 주최 관계는 유지한다.

### 매치 수정

확정 규칙:

- 주최자만 수정할 수 있다.
- 취소되거나 시작한 매치는 수정할 수 없다.
- 정원 감소 결과가 `CONFIRMED` 참가자 수보다 작을 수 없다.
- 정원 증가로 `CLOSED`가 자동 해제되지 않는다.

초기 정책:

- 제목과 안내 사항은 시작 전까지 수정 가능
- 권장 실력, 코트와 시간은 주최자를 제외한 활성 일반 참가자가 없을 때만 수정 가능

### 참가 상태와 전이 — 확정

| 현재 상태 | 사건 | 다음 상태 | 조건 |
|---|---|---|---|
| 관계 없음 | 최초 참가 | `CONFIRMED` | 매치가 참가 가능하고 남은 자리가 있음 |
| `CONFIRMED` | 회원 취소 | `CANCELLED_BY_MEMBER` | 시작 전 |
| `CANCELLED_BY_MEMBER` | 재참가 | `CONFIRMED` | 매치가 참가 가능하고 남은 자리가 있음 |
| `CONFIRMED` | 매치 취소 | `CANCELLED_BY_MATCH` | 주최자의 정상 취소 명령 |
| `CANCELLED_BY_MATCH` | 재참가 | 전이 없음 | 항상 불가 |

- 한 회원은 한 매치에 하나의 참가 관계만 가진다.
- `UNIQUE(match_id, member_id)`를 DB 방어선으로 우선 검토한다.
- 중복 참가 요청으로 활성 관계가 중복 생성되어서는 안 된다.
- 중복 취소로 자리가 두 번 복구되어서는 안 된다.
- 매치 취소 시 모든 활성 참가를 `CANCELLED_BY_MATCH`로 변경한다.
- 매치 취소와 활성 참가 변경은 같은 유스케이스 트랜잭션에서 함께 성공하거나 롤백한다.

### 정원 불변식 — 확정

- 활성 참가자는 `status = CONFIRMED`인 참가 관계다.
- 활성 참가자 수는 `maxParticipants`를 초과할 수 없다.
- `remainingSlots = maxParticipants - confirmedCount`는 0보다 작을 수 없다.
- 실패한 참가 요청은 참가 상태와 정원에 영향을 주지 않는다.
- 주최 관계와 참가 관계는 독립적이다.

### 권장 실력

- 권장 실력은 참가 제한이 아니라 안내 정보다.
- 코드 후보는 `ANY`, `INTRODUCTORY`, `BEGINNER`, `INTERMEDIATE_OR_ABOVE`다.
- 성별, 연령과 실력 자동 비교를 참가 조건으로 사용하지 않는다.

## 미리 확정하지 않는 구현 기술

다음 수단은 문제와 재현 조건을 확인한 뒤 비교한다.

- 비관적 락, 낙관적 락, 조건부 원자적 UPDATE
- 멱등성 키
- Redis, 캐시, 메시지 큐, 비동기 이벤트, Outbox
- 분산 락, 마이크로서비스, CQRS

## 열린 결정

| 항목 | 선택지 | 현재 추천안 | 결정 시점 |
|---|---|---|---|
| 현재 참가 인원 처리 | Match 저장 / 참가 행 집계 / 혼합 | 없음 | 참가 저장·조회 설계 전 |
| 마지막 자리 동시 참가 | 비관적 락 / 낙관적 락 / 조건부 UPDATE 등 | 없음 | 동시 참가 재현 테스트 후 |
| 반복 참가 취소 응답 | 멱등한 204 / 409 상태 충돌 | 없음 | 참가 취소 구현 전 |
| Repository 인터페이스 위치 | domain / application | 없음 | 첫 영속성 유스케이스 구현 전 |
| 세부 패키지 | 계층형 / 기능 중심 변형 | 필요한 코드가 생길 때만 생성 | 각 수직 기능 구현 시 |
| 회원 상태 | 상태 없음 / 최소 상태 도입 | 없음 | 탈퇴·정지 요구가 생길 때 |
| 닉네임 중복 | 허용 / 전역 유일 | 없음 | 회원가입 구현 전 |
| 문자열 길이 | 현재 후보 유지 / 사용성에 따라 조정 | 현재 값을 출발점으로 사용 | DTO·컬럼 구현 전 |
| 최대 정원 상한 | 상한 없음 / 업무 상한 | 없음 | 매치 생성 검증 전 |
| 시간·타임존 | UTC 저장 / 지역 시각 보존 등 | 없음 | Match 영속화 전 |
| 성공 응답 래퍼 | 직접 반환 / 공통 래퍼 | 직접 반환 | 첫 API 구현 전 |
| 페이지 계약 | 0/1 기반, Page/Slice | 0 기반 Page | 목록 API 구현 전 |
| 최종 인덱스 | 초기 후보 / 쿼리·실행 계획 후 조정 | 측정 후 결정 | 조회 구현 후 |
| CSRF 초기화 | 별도 API / 쿠키·헤더 활용 | XSRF-TOKEN 쿠키 전달 우선 검토 | 인증 구현 전 |
| 정원 도달·매치 취소 시 모집 상태 갱신 | 컬럼 변경 / 파생 조건으로만 차단 | 없음 | Match·Participation 구현 전 |

## 재검토 조건

- 동시 참가 테스트에서 정원 불변식 위반 또는 과도한 충돌이 재현됨
- 참가 취소·재참가 또는 매치 취소에서 부분 성공 가능성이 발견됨
- 실제 조회 요구가 현재 필터와 정렬로 표현되지 않음
- 세션 인증과 CSRF 흐름이 클라이언트 구조와 맞지 않음
- 2차 MVP 요구가 현재 도메인 경계에 영향을 줌
- 구현·테스트 결과와 문서가 다름

재검토할 때는 해결책보다 문제, 불변식과 재현 조건을 먼저 기록한다.
