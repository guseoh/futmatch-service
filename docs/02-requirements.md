# 1차 MVP 기능 요구사항

> 문서 상태: 구현을 시작하기 위한 초기 요구사항 기준선이다. 승인된 업무 규칙은 보존하되 API URI, 문자열 길이, 응답 형태와 내부 구현은 변경될 수 있다.

결정 상태의 의미와 범위 판단 기준은 [1차 MVP 결정 기록](./01-decisions.md)을 따른다. HTTP 계약과 오류 코드의 상세 초기안은 [API 명세](./06-api-spec.md)를 따른다.

## 대상 사용자와 관계

| 대상 | 할 수 있는 일 | 권한 기준 |
|---|---|---|
| 비회원 | 구장·코트 조회, 매치 목록·상세 조회 | 공개 API |
| 로그인 회원 | 프로필 관리, 매치 개설, 참가·참가 취소, 내 매치 조회 | 인증 필요 |
| 특정 매치의 주최자 | 해당 매치 수정, 모집 마감·재개, 매치 취소, 참가자 목록 조회 | 인증 + Match의 주최자 관계 확인 |
| 특정 매치의 참가자 | 참가 관계 조회·취소, 조건 충족 시 재참가 | 인증 + MatchParticipation 상태 확인 |

- **확정:** 주최자와 참가자는 전역 Role이 아니라 매치별 관계이며 서로 독립적이다.
- **초기안:** 전역 Role 코드는 `USER`, `ADMIN`을 후보로 둔다. 1차 MVP의 일반 기능은 `USER`가 수행하며 운영자 관리 기능은 범위 밖이다.
- **확정:** 주최자도 참가를 선택하면 MatchParticipation을 가지며 정원 계산에서 다른 참가자와 동일하게 취급한다.

## 1차 MVP 사용자 흐름

### 참가자 정상 흐름

1. 비회원 또는 회원이 기본 조건에 맞는 매치를 탐색한다(`MAT-001`).
2. 매치 상세에서 시간, 코트, 모집 상태, 정원과 남은 자리를 확인한다(`MAT-002`).
3. 비회원이면 로그인한 뒤(`AUTH-001`) 참가를 요청한다(`PAR-001`).
4. 서버는 Match 상태, 모집 상태, 시작 시각, 기존 참가 관계와 남은 자리를 함께 검증한다.
5. 모든 조건이 맞으면 참가 관계가 `CONFIRMED`가 되고 논리적 남은 자리가 하나 줄어든다. 실패하면 참가 상태와 정원에는 변화가 없다.
6. 회원은 내 참가 매치에서 결과를 확인한다(`PAR-003`).
7. 시작 전 참가를 취소하면 상태가 `CANCELLED_BY_MEMBER`가 되고 논리적 남은 자리가 하나 복구된다(`PAR-002`).

### 주최자 정상 흐름

1. 회원이 로그인하고 구장과 소속 코트를 조회한다(`AUTH-001`, `VEN-001`~`VEN-003`).
2. 코트, 제목, 안내 사항, 권장 실력, 시작·종료 시각, 정원과 주최자 참가 여부를 입력해 매치를 개설한다(`MAT-003`).
3. 매치는 `SCHEDULED`·`OPEN`으로 시작한다. 주최자가 참가를 선택하면 주최자의 `CONFIRMED` 참가 관계도 만들어져 정원에 포함된다.
4. 주최자는 내가 주최한 매치와 참가자 목록을 확인한다(`MAT-008`, `PAR-004`).
5. 허용 범위에서 매치를 수정하거나 모집을 마감한다(`MAT-004`, `MAT-005`). 남은 자리가 있을 때 모집을 재개할 수 있다(`MAT-006`).
6. 매치를 취소하면 Match는 `CANCELLED`가 되고 모든 `CONFIRMED` 참가가 `CANCELLED_BY_MATCH`가 된다(`MAT-007`). 두 변화는 함께 성공하거나 함께 롤백한다.

### 취소와 재참가 흐름

1. `CONFIRMED` 회원이 `현재 시각 < startAt`일 때 참가를 취소한다.
2. 상태는 `CANCELLED_BY_MEMBER`가 되고 활성 참가자 수가 하나 감소한다. 주최자 본인이어도 주최자 관계는 그대로다.
3. 같은 회원이 다시 참가를 요청하면 기존 행을 중복 생성하지 않고 기존 관계의 상태 전이를 시도한다.
4. Match가 `SCHEDULED`, 모집이 `OPEN`, 시작 전이고 남은 자리가 있으면 `CONFIRMED`로 재참가한다.
5. `CANCELLED_BY_MATCH`에서는 재참가할 수 없다. 매치가 취소·시작됐거나 모집이 닫혔거나 정원이 찼어도 재참가는 실패한다.
6. 반복 취소 요청의 HTTP 응답 정책은 열린 결정이지만, 어떤 정책에서도 활성 참가자 수가 두 번 감소하거나 자리가 두 번 복구되어서는 안 된다.

## 권한 요구사항

| 기능 | 공개 | 로그인 회원 | 해당 주최자만 |
|---|:---:|:---:|:---:|
| 구장·코트 조회 | O | O | - |
| 매치 목록·상세 | O | O | - |
| 회원가입·로그인 | O | - | - |
| 로그아웃·현재 회원·내 프로필 | - | O | - |
| 매치 개설 | - | O | - |
| 매치 참가·참가 취소·내 참가 매치 | - | O | - |
| 내가 주최한 매치 | - | O | - |
| 매치 수정·모집 마감·재개·취소 | - | - | O |
| 해당 매치 참가자 목록 | - | - | O |

인증되지 않은 보호 API 요청과 인증 자격 증명 실패는 401 계열로, 인증됐지만 주최자 소유권 등이 없는 요청은 403 계열로 구분한다. 존재하지 않는 리소스와 현재 상태의 충돌도 각각 404와 409 계열로 구분한다. 세부 코드는 API 명세의 초기 카탈로그를 따른다.

## 기능 요구사항

아래 URI는 **초기안**이다. 기능 ID와 업무 결과가 기준이며 최종 요청·응답 계약은 API 명세에서 관리한다.

### 회원·인증

| ID | 목적·사용자 | 선행 조건 | 정상 결과와 주요 상태 변화 | 대표 실패 조건 | 관련 API 후보 |
|---|---|---|---|---|---|
| `MEM-001` | 비회원이 계정을 생성 | email·password·nickname 요청이 유효함 | 회원 생성; 이후 로그인 가능한 상태 | 형식·필수값 오류, email 중복, nickname 중복 정책에 따른 충돌 | `POST /api/members` |
| `MEM-002` | 회원이 자신의 최소 프로필을 조회 | 로그인됨 | 프로필 반환; 상태 변화 없음 | 미인증, 회원을 찾을 수 없음 | `GET /api/members/me/profile` |
| `MEM-003` | 회원이 허용된 프로필 필드를 수정 | 로그인됨; 요청 필드가 유효함 | 프로필 갱신 | 미인증, 공백·길이 오류, nickname 중복 정책에 따른 충돌 | `PATCH /api/members/me/profile` |
| `AUTH-001` | 회원이 자격 증명으로 로그인 | 유효한 email·password | 인증 세션 수립 **추천안** | 자격 증명 불일치; email 존재 여부는 노출하지 않음 | `POST /api/auth/login` |
| `AUTH-002` | 로그인 상태를 종료 | 로그인됨 | 현재 인증 상태 종료 | 미인증 요청 처리 세부 정책 | `POST /api/auth/logout` |
| `AUTH-003` | 클라이언트가 현재 로그인 회원을 확인 | 로그인됨 | 현재 회원 식별 정보 반환; 상태 변화 없음 | 미인증, 회원을 찾을 수 없음 | `GET /api/auth/me` |
| `AUTH-004` | **열린 결정:** 세션 인증 클라이언트의 CSRF 토큰 초기화 | 최종 CSRF 흐름이 정해짐 | 토큰 전달; 업무 데이터 변화 없음 | CSRF 설정·세션 흐름에 따른 실패 | 별도 초기화 API 후보; 형태 미정 |

`MEM-002`는 사용자 프로필 리소스 조회이고 `AUTH-003`은 현재 인증 주체를 확인하는 경량 인증 문맥 조회다. 두 응답을 합칠지 여부는 구현 전 API 계약에서 재검토할 수 있다.

### 구장·코트

| ID | 목적·사용자 | 선행 조건 | 정상 결과와 주요 상태 변화 | 대표 실패 조건 | 관련 API 후보 |
|---|---|---|---|---|---|
| `VEN-001` | 누구나 준비된 구장 목록을 조회 | 없음 | 구장 목록 반환; 상태 변화 없음 | 잘못된 목록 조건 | `GET /api/venues` |
| `VEN-002` | 누구나 구장 상세를 조회 | venueId가 존재 | 구장 정보 반환; 상태 변화 없음 | 구장 없음 | `GET /api/venues/{venueId}` |
| `VEN-003` | 누구나 구장에 속한 코트를 조회 | venueId가 존재 | 해당 구장의 코트만 반환; 상태 변화 없음 | 구장 없음 | `GET /api/venues/{venueId}/courts` |

구장과 코트는 운영자가 준비한 시드 데이터를 사용한다. 일반 사용자의 등록·수정 API와 실제 대관 가능 여부 조회는 만들지 않는다.

### 매치

| ID | 목적·사용자 | 선행 조건 | 정상 결과와 주요 상태 변화 | 대표 실패 조건 | 관련 API 후보 |
|---|---|---|---|---|---|
| `MAT-001` | 누구나 매치를 탐색·필터링 | 목록 조건이 유효함 | 기본값으로 `SCHEDULED`·`OPEN`·시작 전·남은 자리 있음 매치 반환; 마감·정원 마감은 명시적 필터로 조회 | 잘못된 페이지·필터·enum | `GET /api/matches` |
| `MAT-002` | 누구나 매치 상세를 확인 | matchId가 존재 | 시간·코트·주최자·상태·정원 정보 반환 | 매치 없음 | `GET /api/matches/{matchId}` |
| `MAT-003` | 로그인 회원이 매치를 개설 | courtId 존재; `endAt > startAt`; 정원과 필수값 유효 | `SCHEDULED`·`OPEN` Match와 주최자 관계 생성; hostParticipates이면 주최자의 `CONFIRMED` 참가 관계 생성 | 미인증, 코트 없음, 시간 범위·정원·필드 오류 | `POST /api/matches` |
| `MAT-004` | 주최자가 시작 전 매치를 수정 | 본인 주최; `SCHEDULED`; 시작 전; 변경별 규칙 충족 | 허용된 필드 갱신; 정원 증가만으로 `CLOSED`가 자동 해제되지는 않음 | 소유권 없음, 시작·취소됨, 잘못된 시간, 정원이 활성 참가자 수보다 작음 | `PATCH /api/matches/{matchId}` |
| `MAT-005` | 주최자가 시작 전 모집을 마감 | 본인 주최; `SCHEDULED`; 시작 전 | 모집 `OPEN → CLOSED` | 소유권 없음, 시작·취소됨, 이미 `CLOSED`인 요청의 처리 정책 | `POST /api/matches/{matchId}/recruitment/close` |
| `MAT-006` | 주최자가 모집을 재개 | 본인 주최; `SCHEDULED`; 시작 전; 남은 자리 있음 | 모집 `CLOSED → OPEN` | 소유권 없음, 시작·취소됨, 남은 자리 없음, 이미 `OPEN`인 요청의 처리 정책 | `POST /api/matches/{matchId}/recruitment/reopen` |
| `MAT-007` | 주최자가 매치를 취소 | 본인 주최; `SCHEDULED`; **초기안:** 시작 전 | Match `SCHEDULED → CANCELLED`; 모든 `CONFIRMED → CANCELLED_BY_MATCH`를 같은 트랜잭션에서 처리 | 소유권 없음, 시작·이미 취소됨 | `POST /api/matches/{matchId}/cancel` |
| `MAT-008` | 회원이 자신이 주최한 매치를 조회 | 로그인됨 | 주최자 관계가 자신인 매치 목록 반환; 상태 변화 없음 | 미인증, 잘못된 목록 조건 | 내 주최 매치 목록 API 후보 |

매치 개설의 핵심 요청 필드는 `courtId`, `title`, `instructions`, `recommendedSkill`, `startAt`, `endAt`, `maxParticipants`, `hostParticipates`다. `maxParticipants >= 1`, 제목·안내 길이와 `startAt`의 미래 시각 검증은 **초기안**이며 최종값은 API·영속화 구현 전에 확정한다.

매치 수정 정책은 다음과 같다.

- **확정:** 주최자만 수정하며 취소되거나 시작한 매치는 수정할 수 없다.
- **확정:** 감소한 정원은 전체 `CONFIRMED` 참가자 수보다 작을 수 없다.
- **초기안:** 제목과 안내 사항은 시작 전까지 수정할 수 있다.
- **초기안:** 권장 실력, 코트와 시간은 주최자를 제외한 `CONFIRMED` 일반 참가자가 없을 때만 수정할 수 있다.
- **초기안:** 부분 수정은 PATCH를 우선 검토한다. 필드 미전송과 명시적 null의 의미는 API 명세에서 구분한다.

### 참가

| ID | 목적·사용자 | 선행 조건 | 정상 결과와 주요 상태 변화 | 대표 실패 조건 | 관련 API 후보 |
|---|---|---|---|---|---|
| `PAR-001` | 로그인 회원이 최초 참가 또는 재참가 | `SCHEDULED`; `OPEN`; 시작 전; 남은 자리 있음; 관계 없음 또는 `CANCELLED_BY_MEMBER` | 없음이면 참가 관계 생성, 취소 이력이면 기존 관계를 `CONFIRMED`로 전이; 활성 수 +1 | 미인증, 매치 없음, 이미 참가, 모집 마감, 정원 마감, 시작·취소됨, `CANCELLED_BY_MATCH` | `POST /api/matches/{matchId}/participations` |
| `PAR-002` | 회원이 자신의 참가를 취소 | 자신의 상태가 `CONFIRMED`; 시작 전 | `CONFIRMED → CANCELLED_BY_MEMBER`; 활성 수 -1; 주최자 관계는 유지 | 미인증, 매치·참가 관계 없음, 비활성 상태, 시작됨; 중복 취소 응답은 열린 결정 | `DELETE /api/matches/{matchId}/participations/me` |
| `PAR-003` | 회원이 자신이 참가한 매치를 조회 | 로그인됨 | 자신의 참가 관계와 매치 목록 반환; 상태 변화 없음 | 미인증, 잘못된 목록 조건 | 내 참가 매치 목록 API 후보 |
| `PAR-004` | 주최자가 해당 매치 참가자를 확인 | 로그인됨; 본인 주최 Match | 참가 관계 목록 반환; 상태 변화 없음 | 매치 없음, 소유권 없음, 잘못된 목록 조건 | `GET /api/matches/{matchId}/participations` |

`PAR-001`의 최초 생성과 재참가는 같은 업무 명령이지만 상태 변화가 다르다. 최초 참가의 201/재참가의 200 사용 여부 등 성공 HTTP 세부 계약은 API 명세의 초기안을 따른다. 동시 요청 해결 기술은 열어 두되, 어떤 구현에서도 정원 불변식과 관계 유일성을 만족해야 한다.

## 정상 흐름의 공통 처리 순서

구체적인 클래스나 락 방식은 확정하지 않지만, 변경 유스케이스는 다음 검증 결과를 일관되게 보장해야 한다.

1. 요청 형식과 필수값을 검증한다.
2. 인증이 필요한 경우 현재 회원을 확인한다.
3. 대상 리소스 존재와 주최자 소유권 또는 참가 관계를 확인한다.
4. Match 상태, 모집 상태와 `현재 시각 < startAt` 조건을 확인한다.
5. 기존 참가 상태와 정원 불변식을 확인한다.
6. 허용된 상태 전이와 필요한 연관 변경을 하나의 유스케이스 단위로 반영한다.
7. 성공 응답 또는 안정적인 오류 코드로 결과를 반환한다.

검사 순서의 내부 구현과 동시성 제어 방식은 열린 결정이다. 외부에서 관찰되는 결과가 동일하고 실패 시 부분 변경이 남지 않아야 한다.

## 대표 오류 흐름

| 상황 | 기대 결과 | 상태 영향 | 오류 분류 후보 |
|---|---|---|---|
| 필수값 누락, null, 빈·공백 문자열, 형식·범위 오류 | 요청 거부 | 없음 | 400 `VALIDATION_FAILED` 또는 `INVALID_REQUEST` |
| 로그인하지 않고 보호 기능 호출 | 인증 요구 | 없음 | 401 `AUTHENTICATION_REQUIRED` |
| 로그인 자격 증명 불일치 | 로그인 실패; email 존재 여부 비공개 | 없음 | 401 `INVALID_CREDENTIALS` |
| 다른 회원이 주최자 명령 호출 | 권한 거부 | 없음 | 403 `MATCH_ACCESS_DENIED` |
| 구장·코트·매치를 찾을 수 없음 | 리소스 없음 | 없음 | 404 계열 NOT_FOUND |
| 이미 `CONFIRMED`인 회원이 다시 참가 | 중복 참가 거부; 새 관계를 만들지 않음 | 없음 | 409 `PARTICIPATION_ALREADY_CONFIRMED` |
| `CLOSED`, 정원 마감, 시작 또는 취소된 매치에 참가 | 참가 거부 | 없음 | 409 상태 충돌 코드 |
| 마지막 한 자리에 동시 참가 | 정원 초과 없이 허용된 요청만 성공; 실패 요청은 무영향 | 성공 요청만 `CONFIRMED` | 409 `MATCH_FULL` 후보; 해결 기술은 열린 결정 |
| 활성 참가자 수보다 작은 정원으로 수정 | 수정 거부 | Match 무변경 | 409 `MATCH_CAPACITY_BELOW_CONFIRMED_COUNT` |
| 남은 자리 없이 모집 재개 | 재개 거부 | `CLOSED` 유지 | 409 `MATCH_REOPEN_NOT_ALLOWED` |
| `CANCELLED_BY_MATCH`에서 재참가 | 재참가 거부 | 참가 상태 유지 | 409 `PARTICIPATION_REJOIN_NOT_ALLOWED` |
| 참가 취소를 반복 | 자리를 두 번 복구하지 않음 | 첫 전이 이후 추가 변화 없음 | HTTP 응답과 오류 코드는 열린 결정 |
| 매치 취소 중 참가 변경 실패 | 전체 취소 롤백 | Match와 모든 참가 상태가 기존 값 유지 | 내부 정보 없는 실패 응답 |

오류 코드명과 HTTP 매핑은 API 명세의 초기 카탈로그가 기준이다. 같은 실패 조건에 서로 다른 의미의 코드를 중복 부여하지 않는다.

## 핵심 업무 규칙과 불변식

1. 한 회원은 한 매치에 하나의 참가 관계만 가진다. `UNIQUE(match_id, member_id)`는 DB 제약 **추천안**이다.
2. 활성 참가자는 `CONFIRMED` 관계만이다. `CANCELLED_BY_MEMBER`, `CANCELLED_BY_MATCH`는 정원에 포함하지 않는다.
3. `confirmedCount <= maxParticipants`이고 `remainingSlots = maxParticipants - confirmedCount >= 0`이어야 한다.
4. 참가하는 주최자도 `CONFIRMED` 관계로 계산한다. 주최자 관계만으로는 정원을 소비하지 않는다.
5. 참가·재참가 실패는 참가 상태와 정원에 영향을 주지 않는다.
6. 중복 참가로 두 관계가 생기거나, 중복 취소로 논리적 자리가 두 번 복구되어서는 안 된다.
7. 매치 취소와 모든 활성 참가의 `CANCELLED_BY_MATCH` 전이는 함께 성공하거나 함께 롤백한다.
8. Match는 Court만 참조한다. Venue는 Court를 통해 찾으며 Match에 중복 저장하지 않는다.
9. 권장 실력은 안내 정보다. 성별·연령·실력 자동 비교를 참가 조건으로 쓰지 않는다.
10. `endAt > startAt`이어야 한다. 참가와 참가 취소는 `현재 시각 >= startAt`이면 허용하지 않는다.
11. 정원을 늘려도 `CLOSED`를 자동으로 `OPEN`으로 바꾸지 않는다.

현재 인원·남은 자리의 저장 여부와 마지막 자리 동시성 제어 방식은 이 불변식을 구현하고 재현 테스트한 뒤 결정한다.

## 주요 상태와 허용 전이

### Match 상태

업무 상태명은 **확정**이다. 저장 타입과 Java enum 구현 방식은 초기안이다.

| 현재 상태 | 사건 | 다음 상태 | 결과 |
|---|---|---|---|
| 생성 전 | 매치 개설 | `SCHEDULED` | 주최자·Court 관계와 모집 상태 생성 |
| `SCHEDULED` | 주최자의 매치 취소 | `CANCELLED` | 활성 참가도 모두 `CANCELLED_BY_MATCH`로 전이 |
| `CANCELLED` | 재활성화 요청 | 전이 없음 | 항상 거부 |

별도 시작·종료 상태 후보는 두지 않는다. 시작 여부는 `현재 시각 >= startAt`으로 판단하고, 이미 시작한 매치는 참가·참가 취소·수정 대상에서 제외한다. 시작 후 매치 취소 허용 여부는 현재 **초기안으로 불허**하며 구현 전 확인한다.

### 모집 상태

업무 상태명은 **확정**이다. 저장 타입과 Java enum 구현 방식은 초기안이다.

| 현재 상태 | 사건 | 다음 상태 | 허용 조건 |
|---|---|---|---|
| 생성 전 | 매치 개설 | `OPEN` | 정상 개설 |
| `OPEN` | 주최자의 모집 마감 | `CLOSED` | Match가 `SCHEDULED`이고 시작 전 |
| `CLOSED` | 주최자의 모집 재개 | `OPEN` | Match가 `SCHEDULED`, 시작 전, 남은 자리 있음 |

남은 자리가 0이면 모집 상태 값과 관계없이 참가할 수 없다. 정원 도달이나 매치 취소 시 모집 상태를 자동 변경할지는 열린 결정이며, 그 결정 전에도 Match 상태·모집 상태·시간·남은 자리를 함께 검사한다.

### 참가 상태

업무 상태명과 전이 규칙은 **확정**이다. 저장 타입과 Java enum 구현 방식은 초기안이다.

| 현재 상태 | 명령 | 다음 상태 | 활성 수 변화 | 허용 조건 |
|---|---|---|---:|---|
| 관계 없음 | 참가 | `CONFIRMED` | +1 | 참가 가능한 Match, 남은 자리 있음 |
| `CONFIRMED` | 회원 취소 | `CANCELLED_BY_MEMBER` | -1 | 시작 전 |
| `CANCELLED_BY_MEMBER` | 재참가 | `CONFIRMED` | +1 | 참가 가능한 Match, 남은 자리 있음 |
| `CONFIRMED` | 매치 취소 | `CANCELLED_BY_MATCH` | -1 | MAT-007 트랜잭션 내부 |
| `CANCELLED_BY_MATCH` | 참가·재참가 | 전이 없음 | 0 | 항상 불가 |

`CANCELLED_BY_MEMBER → CANCELLED_BY_MATCH`처럼 승인되지 않은 전이는 만들지 않는다. 매치 취소 시점에 이미 회원 취소 상태인 관계는 그대로 비활성 상태이며, 활성 관계만 `CANCELLED_BY_MATCH`로 바꾼다.

## 1차 MVP 완료 조건

다음 조건을 모두 만족하면 기능 범위 관점에서 1차 MVP가 완료된 것으로 본다.

- `MEM-001`~`MEM-003`, `AUTH-001`~`AUTH-003`, `VEN-001`~`VEN-003`, `MAT-001`~`MAT-008`, `PAR-001`~`PAR-004`의 정상 흐름이 구현된다.
- `AUTH-004`는 CSRF 흐름 결정에 따라 구현하거나 불필요한 이유와 대안을 기록한다.
- 공개·로그인·주최자 소유권 경계가 권한 표와 일치하고 401·403이 구분된다.
- 참가, 취소, 재참가와 매치 취소가 허용된 상태 전이만 만든다.
- 중복 참가·중복 취소와 마지막 자리 동시 요청에서도 관계 유일성, 정원 상한과 실패 무영향 불변식이 유지된다.
- 매치 취소와 활성 참가 취소가 하나의 유스케이스에서 원자적으로 처리된다.
- 기본 탐색과 마감·정원 마감 필터, 내 참가 매치, 내 주최 매치와 주최자 참가자 목록을 조회할 수 있다.
- 운영자가 준비한 구장·코트 시드 데이터로 매치를 개설할 수 있고, Match가 Venue를 중복 참조하지 않는다.
- 대표 검증·인증·권한·리소스 없음·상태 충돌 오류가 API 명세의 일관된 응답 형식으로 반환된다.
- 팀, 대기자, 승인제, 자동 매칭, 알림, 평가, 운영자 관리, 실제 코트 예약, 결제·환불·PG 웹훅이 1차 MVP 구현 범위에 섞이지 않는다.
- 구현과 테스트에서 확정된 새로운 사실, 초기안의 변경과 열린 결정의 결론이 관련 설계 문서에 반영된다.
