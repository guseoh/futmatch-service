# 인증·인가 초기 설계

이 문서는 1차 MVP의 인증·인가 기준선이다. 업무 수준의 접근 규칙은 **확정**하고, Spring Security 세부 구성과 세션 구현 방식은 구현 단계의 선택으로 남긴다. 공통 요청·응답 및 오류 계약은 [API 명세](./06-api-spec.md)를 따른다.

## 1. 기본 방향

### 세션 인증 우선 검토

**추천안:** Spring Security 기반 서버 세션 인증을 1차 MVP의 출발점으로 사용한다.

- 브라우저 중심 단일 백엔드 MVP에서 로그아웃과 인증 상태 폐기를 서버가 직접 통제하기 쉽다.
- 토큰 발급·재발급·폐기 체계를 먼저 설계하지 않고 회원·매치·참가 업무 규칙에 집중할 수 있다.
- 동일 출처 웹 애플리케이션과 쿠키 사용을 전제로 CSRF 방어를 일관되게 적용할 수 있다.

이 추천은 `SecurityFilterChain`, `AuthenticationProvider`, 로그인 필터, Principal 클래스, 성공·실패 핸들러나 세션 저장소의 구체 구성을 확정하지 않는다. 다중 서버 운영, 별도 모바일 클라이언트, 외부 API 개방 또는 세션 운영 비용이 실제 요구로 나타나면 인증 방식을 재검토한다.

### 인증 주체와 관계 권한

- **확정:** 전역 역할 후보는 `USER`, `ADMIN`이다. 1차 MVP의 일반 기능은 `USER`를 기준으로 하며 운영자 관리 기능은 범위 밖이다.
- **확정:** `Host`와 `Participant`는 전역 역할이 아니다. 각각 특정 매치의 `host_member_id` 관계와 활성 참가 관계로 판단한다.
- **확정:** 주최자 관계와 참가 관계는 독립적이다. 주최자가 참가를 취소해도 주최자 소유권은 유지된다.
- **열린 결정:** 회원 상태 enum과 탈퇴·정지 정책은 확정하지 않는다. 상태가 도입되면 로그인 허용, 세션 무효화, 기존 매치·참가 데이터 보존 규칙을 함께 결정한다.

## 2. 인증 흐름

아래 URI는 [API 명세](./06-api-spec.md)의 **초기 추천 계약**과 함께 관리한다.

### 2.1 회원가입

1. 클라이언트가 `email`, `password`, `nickname`을 제출한다.
2. 서버는 형식·필수값을 검증하고 이메일 중복을 확인한다. 닉네임 중복 금지 여부는 열린 결정이다.
3. 비밀번호를 단방향 적응형 해시로 변환한 뒤 회원을 생성한다. 원문 비밀번호는 저장하거나 로그에 남기지 않는다.
4. 생성된 회원의 공개 가능한 필드만 반환한다.

**초기안:** 회원가입 성공이 자동 로그인을 의미하지 않는다. 자동 로그인 여부를 바꾸려면 세션 고정 공격 방어와 클라이언트 흐름을 함께 재검토한다.

### 2.2 로그인

1. 클라이언트가 `email`, `password`를 제출한다.
2. 서버는 자격 증명을 검증한다.
3. 성공 시 인증된 세션을 수립하고 세션 식별자를 안전한 쿠키로 전달한다.
4. 기존 익명 세션이 있었다면 로그인 시점에 세션 식별자 변경 또는 동등한 세션 고정 방어를 적용한다.

**확정:** 로그인 실패 응답은 이메일 존재 여부, 회원 상태의 내부 사유, 비밀번호의 어느 부분이 틀렸는지를 구분해 노출하지 않고 `INVALID_CREDENTIALS`로 통일한다.

**초기안:** 로그인 성공은 현재 회원 요약을 `200 OK` 본문으로 반환한다. 세션 쿠키의 이름, 만료 시간, `SameSite`, `Secure`, 영속 세션 여부는 배포 환경과 프론트엔드 출처가 정해질 때 확정한다. `HttpOnly`는 세션 쿠키의 기본 보안 원칙으로 삼는다.

### 2.3 로그아웃

1. 인증된 클라이언트가 로그아웃을 요청한다.
2. 서버는 현재 인증 세션을 무효화하고 세션 쿠키를 만료시킨다.
3. **초기 추천:** 성공 시 본문 없이 `204 No Content`를 반환한다.

로그아웃은 상태 변경 요청이므로 쿠키 기반 세션을 사용할 때 CSRF 보호 대상에 포함한다.

### 2.4 현재 회원과 프로필

- 현재 로그인 회원 조회는 세션의 인증 주체를 애플리케이션 계층이 사용할 수 있는 회원 식별자로 변환한 뒤 최신 회원 정보를 조회한다.
- 내 프로필 조회·수정은 인증 주체 자신의 리소스에만 허용한다.
- **초기안:** 현재 회원 조회는 인증 상태와 화면 초기화에 필요한 최소 요약을, 프로필 조회는 수정 화면에 필요한 프로필을 반환한다. 실제 응답이 완전히 같아지면 구현 중 하나로 통합할 수 있다.
- 프로필 수정에서 이메일·비밀번호 변경은 1차 MVP 최소 범위에 포함하지 않는다. 닉네임 등 API 명세에 명시한 필드만 변경한다.

## 3. 접근 제어 기준

### 3.1 공개 API

인증 없이 허용한다.

- 매치 목록 조회
- 매치 상세 조회
- 구장 목록·상세 조회
- 구장별 코트 목록 조회
- 회원가입과 로그인
- **초기안:** CSRF 토큰 초기화 API 후보

공개 매치 응답은 로그인 여부에 따라 리소스 존재 자체가 달라지지 않아야 한다. 현재 사용자 관계에서 계산하는 편의 필드는 비인증 시 `false` 또는 명세에 정의한 기본값을 사용하고, 필드 생략 여부를 클라이언트마다 다르게 처리하지 않는다.

### 3.2 인증 필요 API

유효한 로그인 세션이 필요하다.

- 로그아웃, 현재 회원 조회, 내 프로필 조회·수정
- 매치 개설
- 매치 참가와 참가 취소
- 내 참가 매치 조회
- 내가 주최한 매치 조회

인증되지 않은 요청은 업무 로직이나 리소스 소유권 검사 전에 `401 Unauthorized`와 `AUTHENTICATION_REQUIRED`로 응답한다.

### 3.3 주최자 소유권 필요 API

로그인 후 요청 회원 ID와 대상 매치의 `host_member_id`가 같은지 확인한다.

- 매치 수정
- 모집 마감
- 모집 재개
- 매치 취소
- 해당 매치 참가자 목록 조회

**확정:** 인증됐지만 주최자가 아니면 `403 Forbidden`이다. 매치가 존재하지 않을 때의 `404`와 비주최자의 `403` 적용 순서는 리소스 존재 정보 노출 정책과 Repository 조회 방식을 구현할 때 결정하되, 동일 API 안에서는 일관되어야 한다.

**추천안:** Controller가 `SecurityContextHolder`에서 직접 핵심 권한을 판단하지 않는다. 웹 계층은 인증된 회원 식별자를 애플리케이션 유스케이스에 전달하고, 유스케이스가 대상 매치와 함께 소유권을 검증한다. 도메인 객체는 Spring Security API에 의존하지 않는다.

## 4. 401, 403, 404 구분

| 상황 | HTTP | 오류 코드 | 원칙 |
|---|---:|---|---|
| 로그인 자격 증명 실패 | 401 | `INVALID_CREDENTIALS` | 계정 존재 여부를 감춘다. |
| 인증이 필요한 API에 세션이 없거나 유효하지 않음 | 401 | `AUTHENTICATION_REQUIRED` | 재인증이 필요함을 뜻한다. |
| 인증됐지만 매치 소유권이 없음 | 403 | `MATCH_ACCESS_DENIED` | 인증 여부와 주최자 관계 부족을 구분한다. 1차 MVP에는 별도의 전역 역할 제한 API가 없다. |
| CSRF 검증 실패 | 403 | `CSRF_TOKEN_INVALID` | 인증 여부와 별개로 위조 방지 검증 실패를 나타낸다. |
| 요청 대상 리소스가 없음 | 404 | 리소스별 `*_NOT_FOUND` | 상태 충돌과 구분한다. |

오류 본문은 [공통 오류 응답](./06-api-spec.md#16-공통-오류-응답-계약)의 초기 형식을 사용하고 스택 트레이스, 내부 예외명, SQL과 인증정보를 노출하지 않는다.

## 5. CSRF 기본 방향

쿠키가 자동 전송되는 세션 인증에서는 상태 변경 요청에 CSRF 방어가 필요하다.

- **확정:** `POST`, `PUT`, `PATCH`, `DELETE` 등 상태 변경 API를 편의상 일괄 면제하지 않는다.
- **추천안:** Spring Security의 CSRF 보호를 유지하고, 브라우저 클라이언트가 읽어 요청 헤더로 돌려보낼 수 있는 토큰 전달 방식을 사용한다.
- **초기안:** 프론트엔드 초기화용 `GET /api/auth/csrf`를 제공하는 계약을 검토한다. 이 API는 토큰 수령만 담당하고 로그인 상태를 만들지 않는다.
- CSRF 토큰 불일치는 `403`과 `CSRF_TOKEN_INVALID`로 정규화하는 후보이며, 내부 필터 응답도 API 공통 오류 형식에 맞추는 방법은 구현 단계에서 정한다.
- CORS와 CSRF는 별개다. 허용 출처, 쿠키 `SameSite`와 `Secure` 값은 실제 배포 토폴로지가 정해진 뒤 함께 결정한다.

**열린 결정:** CSRF 초기화 API의 최종 URI·응답 필드, 쿠키 저장소와 헤더 이름은 프론트엔드 통합 시점에 확정한다. 변경 시 API 명세, 보안 설정과 클라이언트 초기화 흐름이 함께 영향을 받는다.

## 6. 비밀번호와 민감정보 원칙

- 비밀번호는 복호화할 수 없는 적응형 해시 함수로 저장한다. **추천안:** Spring Security가 지원하는 `PasswordEncoder` 계열을 사용하되 구체 알고리즘과 비용 계수는 성능 측정과 운영 기준으로 선택한다.
- 원문 비밀번호, 세션 식별자와 CSRF 토큰을 애플리케이션 로그에 남기지 않는다.
- 검증 오류의 `rejectedValue`에 비밀번호나 인증정보를 포함하지 않는다.
- 회원 응답, 매치의 주최자 응답과 참가자 목록에 비밀번호 해시, 세션 정보 또는 불필요한 개인정보를 포함하지 않는다.
- 로그인 실패 횟수 제한, 계정 잠금과 감사 이벤트는 1차 MVP에서 확정하지 않는다. 보안 위험 또는 운영 요구가 확인되면 회원 상태 정책과 함께 재검토한다.

## 7. 회원 상태와 탈퇴·정지

현재 회원 상태 enum, 탈퇴와 정지 정책은 **열린 결정**이다.

| 항목 | 현재 상황 | 선택지 | 현재 추천안 | 결정 시점 | 변경 영향 |
|---|---|---|---|---|---|
| 회원 상태 | MVP에 가입·로그인만 확정됨 | 상태 없음 / 활성·정지·탈퇴 상태 도입 | 추천안 없음 | 탈퇴 또는 운영자 제재 요구사항을 구현하기 전 | 회원 테이블, 로그인 허용 규칙, 세션 무효화, 오류 코드 |
| 탈퇴 개인정보 | 보존 기간과 법적 요구가 정해지지 않음 | 즉시 삭제 / 익명화 / 제한 보존 | 추천안 없음 | 탈퇴 기능 범위를 결정할 때 | 주최 매치·참가 이력 참조, 개인정보 처리 정책 |
| 닉네임 중복 | 중복 허용 여부가 승인되지 않음 | 허용 / 전체 회원 유일 | 추천안 없음 | 프로필 구현과 DB 제약 확정 전 | 가입·수정 검증, UNIQUE 제약, 오류 코드 |

이 결정 전에는 존재하지 않는 정지·탈퇴 상태, 복구 API나 운영자 API를 1차 MVP 계약에 추가하지 않는다.

## 8. 인증 관련 오류와 명세 연결

| 오류 코드 | 대표 HTTP | 대표 발생 위치 | 공개 정보 원칙 |
|---|---:|---|---|
| `AUTHENTICATION_REQUIRED` | 401 | 인증 필요 API의 무인증 요청 | 세션 내부 사유를 노출하지 않는다. |
| `INVALID_CREDENTIALS` | 401 | 로그인 실패 | 이메일 존재 여부와 실패 상세를 통합한다. |
| `MATCH_ACCESS_DENIED` | 403 | 주최자 소유권 부족 | 대상 매치의 민감 정보를 포함하지 않는다. |
| `CSRF_TOKEN_INVALID` | 403 | CSRF 검증 실패 | 기대 토큰과 전달 토큰을 반환하지 않는다. |
| `MEMBER_NOT_FOUND` | 404 | 현재 회원 데이터가 존재하지 않음 | 내부 식별자 외의 개인정보를 노출하지 않는다. |
| `MEMBER_EMAIL_DUPLICATED` | 409 | 회원가입 이메일 충돌 | 가입 API에 한해 중복 충돌을 알린다. 로그인에는 사용하지 않는다. |
| `MEMBER_NICKNAME_DUPLICATED` | 409 | 닉네임 유일 정책을 선택한 경우 | **열린 결정:** 정책 확정 전 조건부 후보다. |

오류 코드의 최종 초기 카탈로그, 본문 필드와 API별 연결은 [API 명세의 오류 코드 카탈로그](./06-api-spec.md#8-오류-코드-카탈로그)를 단일 기준으로 삼는다.

## 9. 구현 시 재검토 항목

- 프론트엔드와 API가 동일 출처인지, 쿠키를 교차 출처로 전송해야 하는지
- 세션 만료, 동시 로그인과 로그아웃 범위
- 로그인 성공 응답과 현재 회원 조회 응답의 중복 정도
- CSRF 초기화 API 및 토큰 전달 계약
- 회원 상태, 탈퇴·정지와 기존 세션 처리
- 사용자 식별자를 웹 계층에서 애플리케이션 계층으로 전달하는 방식
- 인증·인가 실패를 공통 오류 본문으로 변환하는 경계
