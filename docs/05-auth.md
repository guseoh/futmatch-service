# 인증·인가 초기 설계

이 문서는 1차 MVP의 인증·인가 기준선이다. 업무 수준의 접근 규칙은 **확정**하고, Spring Security 세부 구성은 구현 단계에서 결정한다. 요청·응답과 오류 코드는 [API 명세](./06-api-spec.md)를 따른다.

## 1. 기본 방향

### 세션 인증 우선 검토

**추천안:** Spring Security 기반 서버 세션 인증을 1차 MVP의 출발점으로 사용한다.

- 브라우저 중심 MVP에서 로그아웃과 인증 상태 폐기를 서버가 직접 통제하기 쉽다.
- 토큰 발급·재발급·폐기 체계를 먼저 만들지 않고 도메인 규칙 구현에 집중할 수 있다.
- 쿠키 기반 인증과 CSRF 방어를 함께 설계할 수 있다.

다음 구현 세부사항은 아직 확정하지 않는다.

- `SecurityFilterChain` 구성
- `AuthenticationProvider` 구성
- Principal 클래스
- 로그인 필터와 성공·실패 핸들러
- 세션 저장소와 만료 정책

다중 서버 운영, 모바일 클라이언트 또는 외부 API 요구가 생기면 인증 방식을 재검토한다.

## 2. 인증 주체와 권한

- 전역 Role 후보는 `USER`, `ADMIN`이다.
- Host와 Participant는 전역 Role이 아니다.
- 주최자는 Match의 `host_member_id`, 참가자는 MatchParticipation 상태로 판단한다.
- 주최 관계와 참가 관계는 독립적이다.
- 주최자가 자신의 참가를 취소해도 주최 권한은 유지된다.

회원 상태 enum과 탈퇴·정지 정책은 열린 결정이다. 상태를 도입하면 로그인 허용, 기존 세션 무효화와 과거 매치·참가 데이터 보존을 함께 결정한다.

## 3. 인증 흐름

### 회원가입

1. 클라이언트가 `email`, `password`, `nickname`을 제출한다.
2. 서버가 필수값·형식과 이메일 중복을 확인한다.
3. 비밀번호를 단방향 적응형 해시로 저장한다.
4. 공개 가능한 회원 정보만 반환한다.

**초기안:** 회원가입 성공 후 자동 로그인하지 않는다.

### 로그인

1. 클라이언트가 `email`, `password`를 제출한다.
2. 서버가 자격 증명을 검증한다.
3. 성공하면 인증 세션을 수립하고 세션 식별자를 쿠키로 전달한다.
4. 로그인 시 세션 식별자를 변경하거나 동등한 세션 고정 공격 방어를 적용한다.

로그인 실패는 이메일 존재 여부나 구체 실패 원인을 노출하지 않고 `INVALID_CREDENTIALS`로 통일한다.

**초기안:** 성공 응답은 현재 회원 요약을 `200 OK`로 반환한다.

### 로그아웃

1. 인증된 클라이언트가 로그아웃을 요청한다.
2. 서버가 현재 세션을 무효화하고 세션 쿠키를 만료시킨다.
3. 성공하면 `204 No Content`를 반환한다.

로그아웃은 상태 변경 요청이므로 CSRF 보호 대상이다.

### 현재 회원과 프로필

- `GET /api/auth/me`를 현재 로그인 회원 조회의 단일 GET 계약으로 사용한다.
- 클라이언트 초기화에 필요한 회원 ID, 이메일, 닉네임과 Role 후보를 반환한다.
- 프로필 수정은 `PATCH /api/members/me/profile`로 분리한다.
- 이메일과 비밀번호 변경은 1차 MVP 최소 범위에 포함하지 않는다.
- 별도 프로필 상세 조회가 실제로 필요해질 때만 새로운 GET API를 추가한다.

## 4. 접근 제어

### 공개 API

- 회원가입
- 로그인
- CSRF 초기화 후보
- 구장 목록·상세와 코트 목록
- 매치 목록·상세

### 로그인 필요 API

- 로그아웃
- 현재 회원 조회
- 내 프로필 수정
- 매치 개설
- 매치 참가·참가 취소
- 내 참가 매치
- 내가 주최한 매치

### 주최자 소유권 필요 API

- 매치 수정
- 모집 마감
- 모집 재개
- 매치 취소
- 참가자 목록 조회

인증된 회원 ID는 웹·보안 경계에서 얻어 애플리케이션 유스케이스에 전달한다. 도메인 객체와 핵심 유스케이스가 `SecurityContextHolder`를 직접 조회하지 않는다.

## 5. 401, 403, 404 구분

| 상황 | HTTP | 오류 코드 |
|---|---:|---|
| 로그인 자격 증명 실패 | 401 | `INVALID_CREDENTIALS` |
| 보호 API에 유효한 세션 없음 | 401 | `AUTHENTICATION_REQUIRED` |
| 인증됐지만 해당 매치 주최자가 아님 | 403 | `MATCH_ACCESS_DENIED` |
| CSRF 검증 실패 | 403 | `CSRF_TOKEN_INVALID` |
| 대상 리소스 없음 | 404 | 리소스별 `*_NOT_FOUND` |

매치가 없을 때 404를 먼저 반환할지, 비주최자에게 403을 먼저 반환할지는 리소스 존재 정보 노출 정책과 조회 방식을 구현할 때 정한다. 같은 API 안에서는 일관되어야 한다.

## 6. CSRF 기본 방향

쿠키가 자동 전송되는 세션 인증에서는 상태 변경 요청에 CSRF 방어가 필요하다.

- `POST`, `PUT`, `PATCH`, `DELETE`를 편의상 일괄 면제하지 않는다.
- Spring Security의 CSRF 보호를 유지한다.
- 브라우저가 CSRF 토큰을 쿠키에서 읽어 요청 헤더로 전달하는 방식을 우선 검토한다.
- **초기 추천:** `GET /api/auth/csrf` 호출 시 `204 No Content`와 `XSRF-TOKEN` 쿠키를 반환한다.
- 로그인 요청도 CSRF 보호 대상이면 로그인 화면 진입 시 위 초기화 흐름을 수행한다.
- 쿠키 이름, 헤더 이름과 저장소 구현은 프론트엔드 통합 시 확정한다.
- CORS, CSRF, `SameSite`, `Secure`는 별개의 문제이므로 실제 배포 출처가 정해질 때 함께 검토한다.

CSRF 오류 응답에는 기대 토큰이나 전달된 토큰을 포함하지 않는다.

## 7. 비밀번호와 민감정보

- 비밀번호는 복호화 가능한 형태로 저장하지 않는다.
- 원문 비밀번호, 세션 식별자와 CSRF 토큰을 로그에 남기지 않는다.
- 비밀번호와 인증정보를 검증 오류의 `rejectedValue`로 반환하지 않는다.
- 회원·참가자 응답에 비밀번호 해시나 불필요한 개인정보를 포함하지 않는다.
- 세션 쿠키는 `HttpOnly`를 기본 보안 원칙으로 검토한다.
- `Secure`, `SameSite`, 만료 시간은 배포 환경에서 확정한다.

로그인 실패 횟수 제한, 계정 잠금과 감사 이벤트는 1차 MVP에서 확정하지 않는다.

## 8. 인증 관련 오류

| 오류 코드 | HTTP | 의미 |
|---|---:|---|
| `AUTHENTICATION_REQUIRED` | 401 | 유효한 로그인 세션이 없음 |
| `INVALID_CREDENTIALS` | 401 | 로그인 자격 증명 실패 |
| `MATCH_ACCESS_DENIED` | 403 | 해당 매치의 주최자 소유권 부족 |
| `CSRF_TOKEN_INVALID` | 403 | CSRF 토큰 없음 또는 불일치 |
| `MEMBER_NOT_FOUND` | 404 | 인증 식별자에 대응하는 회원 데이터 없음 |
| `MEMBER_EMAIL_DUPLICATED` | 409 | 회원가입 이메일 충돌 |
| `MEMBER_NICKNAME_DUPLICATED` | 409 | 닉네임 유일 정책을 선택한 경우의 충돌 |

닉네임 중복 오류는 정책이 확정되기 전까지 조건부 후보로 둔다.

## 9. 열린 결정

| 항목 | 선택지 | 결정 시점 |
|---|---|---|
| 세션 만료와 동시 로그인 | 단일/다중 세션, 만료 시간 | 인증 구현 전 |
| CSRF 쿠키·헤더 이름 | Spring 기본/커스텀 | 프론트엔드 연동 전 |
| 회원 상태 | 상태 없음/활성·정지·탈퇴 | 탈퇴·제재 기능 전 |
| 탈퇴 개인정보 | 삭제/익명화/제한 보존 | 탈퇴 요구 설계 시 |
| 닉네임 중복 | 허용/전역 유일 | 회원가입 구현 전 |
| 인증 실패 변환 위치 | Security 핸들러/공통 오류 어댑터 | 보안 설정 구현 시 |

새로운 결정은 [결정 기록](./01-decisions.md)과 [API 명세](./06-api-spec.md)에 함께 반영한다.
