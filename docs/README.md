# 1차 MVP 설계 문서

이 디렉터리의 문서는 풋살 예약·매칭 서비스 1차 MVP 백엔드 구현을 시작하기 위한 **초기 설계 기준선**이다. 구현과 검증 과정에서 학습한 사실을 반영해 계속 갱신하며, 최종 불변 문서로 취급하지 않는다.

## 문서 상태 표기

| 표기 | 의미 |
|---|---|
| **확정** | 현재 승인된 업무 규칙 또는 범위다. 변경하려면 변경 이유와 영향을 기록하고 명시적으로 재결정한다. |
| **초기안** | 구현을 시작하기 위해 임시로 구체화한 값이나 계약이다. 구현 경험과 테스트 결과에 따라 바뀔 수 있다. |
| **추천안** | 현재 정보에서 우선 적용할 선택지다. 대안 비교 후 다른 선택을 할 수 있다. |
| **열린 결정** | 근거가 부족하거나 구현 과정의 검증이 필요한 항목이다. 결정 시점과 변경 영향을 함께 관리한다. |

표기가 없는 문장은 해당 절에서 선언한 상태를 따른다. 특히 패키지명, 문자열 길이, 페이지 크기, URI 세부 형태와 인덱스는 별도 표기가 없더라도 구현 세부사항으로 오해하지 않도록 각 문서에서 상태를 명시한다.

## 권장 읽기 순서

1. [결정 기록](./01-decisions.md): 목표, 범위, 승인된 규칙과 열린 결정을 먼저 확인한다.
2. [요구사항](./02-requirements.md): 사용자 흐름, 기능 요구사항, 권한과 상태 전이를 확인한다.
3. [아키텍처](./03-architecture.md): 도메인 경계, 책임과 의존 방향을 확인한다.
4. [ERD](./04-erd.md): 데이터 관계, 제약 후보와 정합성 위험을 확인한다.
5. [인증·인가](./05-auth.md): 세션 인증 후보, 접근 제어와 CSRF 방향을 확인한다.
6. [API 명세](./06-api-spec.md): 요청·응답 계약, HTTP 정책과 오류 코드로 구현 경계를 확인한다.

## 사용 원칙

- 구현 전에 관련 요구사항 ID, 업무 규칙, 데이터 제약 후보와 API 계약을 함께 확인한다.
- 구현 또는 테스트에서 새로운 사실, 충돌, 재현 가능한 위험을 발견하면 관련 문서의 결정 상태와 근거를 갱신한다.
- 락, 참가 인원 저장 방식, Repository 쿼리와 같은 구현 해법은 문제와 불변식이 재현되기 전에 확정하지 않는다.
- 문서와 실제 코드가 다르면 먼저 코드와 자동화된 테스트 결과를 확인한다. 차이가 의도된 변경이면 문서를 갱신하고, 의도되지 않은 변경이면 승인된 업무 규칙을 기준으로 코드와 테스트를 재검토한다.
- 2차 MVP 이후 항목은 방향만 기록한다. 1차 MVP 문서에 결제·환불·실제 코트 대관의 API, 테이블 또는 상태를 미리 추가하지 않는다.
